PRD-002: Rodaje IA — Herramienta de continuidad visual para series generadas con IA

## Contexto y Problema

Los creadores de series generadas con IA producen contenido audiovisual protagonizado por personajes humanos creados íntegramente mediante inteligencia artificial. En el proceso intervienen distintos roles: uno se encarga de la escritura de los guiones y otro de transformar esos guiones en contenido visual, definiendo escenas, planos, cámaras, iluminación y demás elementos de producción. El riesgo principal es que, al generar cada escena por separado, los personajes pierdan consistencia visual entre tomas y episodios (cambien de cara, ropa, edad, etc.), y que el resultado final se vea "genérico de IA" en vez de profesional.

Hoy ese trabajo de especificar plano, cámara e iluminación para cada escena se hace a mano, de forma artesanal, escena por escena — es lento y depende 100% del criterio de quien produce en el momento, sin un sistema que lo sostenga.

**Personas:**
- **Productor/a de contenido** — gestiona personajes, carga guiones, revisa/ajusta fichas técnicas y prompts, genera el contenido final. Necesita que la consistencia visual entre escenas sea automática, no algo que tenga que sostener a mano.
- **Guionista** — escribe los guiones y los entrega como texto siguiendo una convención de formato acordada. Necesita que su formato de entrega sea simple y no le exija herramientas extra.

## Objetivos

- Que la consistencia visual de cada personaje (aspecto, vestuario, edad) se mantenga automáticamente entre escenas y episodios, sin trabajo manual repetido, y que esto se pueda **verificar**, no solo asumir.
- Que la producción se vea profesional y casi no se note que está hecha con IA, como base para escalar a varias series en paralelo.
- Reducir el tiempo de especificar plano/cámara/iluminación por escena, hoy 100% manual, a un proceso asistido que el/la productor/a solo revisa y ajusta.

*(A nivel producto, "ganar" en v1 significa: cargar un guion y obtener fichas técnicas + prompts consistentes con las hojas de personaje — de forma comprobable, no solo por diseño — sin intervención manual escena por escena.)*

## Requerimientos Funcionales

- RF-01: El sistema debe permitir crear y gestionar múltiples series, cada una con su propio conjunto de hojas de personaje (nombre, descripción física, vestuario, personalidad, rol).
- RF-01b: El sistema debe permitir definir, para un personaje de una serie, **overrides a nivel episodio** sobre su hoja base (ej: vestuario o rasgo físico distinto a partir del episodio N). Al generar la ficha técnica y el prompt de una escena, el sistema debe usar la hoja base combinada con el override vigente para el episodio de esa escena, sin que el/la productor/a tenga que recalcularlo a mano.
- RF-02: El sistema debe permitir cargar el guion de un episodio como texto plano, asociado a una serie y episodio existentes.
- RF-03: El sistema debe validar que el guion recibido respete la convención de formato (escenas marcadas con `ESCENA N — LUGAR — MOMENTO DEL DÍA`, diálogo marcado como `PERSONAJE:`) y debe avisar si el formato es inválido, sin intentar procesarlo igual. En v1, un guion inválido queda rechazado por completo: no se guarda una versión parcial ni se genera nada, y el sistema no propone una corrección automática — la responsabilidad de reenviarlo corregido es del/de la guionista.
- RF-04: El sistema debe dividir el guion en escenas y, dentro de cada una, separar el bloque de acción de las líneas de diálogo, de forma determinística (sin usar IA para este paso).
- RF-05: El sistema debe identificar qué personajes están presentes en cada escena — incluyendo los mencionados solo en el bloque de acción sin línea de diálogo propia — buscando de forma determinística, dentro del texto de la escena (acción + diálogo), los nombres de las hojas de personaje ya cargadas para esa serie. Este paso no usa IA.
- RF-06: El sistema debe generar, por cada escena, una ficha técnica (tipo de plano, tipo de cámara/lente, tipo de iluminación) usando IA, a partir del bloque de acción, el encabezado de escena (lugar/momento del día) y la(s) hoja(s) de personaje correspondiente(s) (incluyendo el override de episodio vigente, si existe, RF-01b). La salida de la IA debe ser estructurada (schema con plano/cámara/iluminación como enums restringidos a la lista cerrada de RNF-04), no texto libre a validar después.
- RF-07: El sistema debe permitir revisar y editar manualmente la ficha técnica generada antes de continuar. Toda edición manual debe reflejarse literalmente en el prompt final (RF-08): el sistema no debe volver a generar ni reinterpretar con IA los campos ya editados a mano.
- RF-08: El sistema debe generar un prompt final por escena, combinando la ficha técnica editada y la descripción del personaje (hoja base + override de episodio vigente, si existe), en un formato listo para copiar y pegar en la IA Generadora de Videos.

## Requerimientos No Funcionales

- RNF-01: El sistema debe soportar episodios de hasta 30 escenas.
- RNF-02: El sistema debe procesar un guion de 20 escenas (desde que se carga hasta que se muestran todas las fichas técnicas generadas) en menos de 3 minutos.
- RNF-03: Si la llamada al modelo de IA para generar una ficha técnica (RF-06) falla o excede el tiempo de espera, el sistema debe reintentar automáticamente una vez. Si el reintento también falla, la escena queda marcada como "pendiente" con un aviso visible, sin bloquear ni descartar el procesamiento del resto del episodio.
- RNF-04: El vocabulario de plano/cámara/iluminación utilizado por el sistema debe provenir de una lista cerrada, versionada y mantenida fuera del código de la aplicación (ej: un archivo de configuración en el repo). El proceso de definición de esa lista (quién la escribe, dónde vive, cómo se actualiza) debe estar acordado antes de implementar RF-06, aunque el contenido final de la lista se define como un entregable aparte, previo a la construcción de pantallas.

## Criterios de Aceptación

- AC-01 (RF-01): Dado que no existe la serie, cuando se crea una serie nueva con al menos un personaje, entonces la serie y su hoja de personaje quedan guardadas y disponibles para asociarse a episodios.
- AC-01b (RF-01b): Dado un personaje con un override definido a partir del episodio 5, cuando se genera la ficha técnica o el prompt de una escena del episodio 5 o posterior, entonces se usan los atributos del override; cuando se genera una escena de un episodio anterior al 5, entonces se usan los atributos de la hoja base.
- AC-02a (RF-02): Dado un guion válido en texto plano, cuando se carga asociado a una serie y episodio existentes, entonces el guion queda registrado y disponible para su procesamiento (RF-04).
- AC-02b (RF-02): Dado un intento de cargar un guion asociado a una serie o episodio inexistente, cuando se envía, entonces el sistema rechaza la carga y no registra nada.
- AC-03 (RF-03): Dado un guion sin encabezados de escena o sin diálogo marcado correctamente, cuando se intenta cargar, entonces el sistema muestra un aviso de formato inválido, no guarda ninguna versión del guion y no genera fichas técnicas.
- AC-04 (RF-04): Dado un guion válido con escenas y diálogo marcados según la convención, cuando se procesa, entonces cada escena queda separada en su bloque de acción y sus líneas de diálogo, sin mezclarlos.
- AC-05 (RF-05): Dado un personaje mencionado solo en la acción de una escena (sin línea de diálogo), cuando se procesa esa escena, entonces el personaje aparece igualmente en la lista de personajes en cuadro, sin haber invocado un modelo de IA para esa detección.
- AC-06 (RF-06): Dado el bloque de acción, el encabezado de escena y una hoja de personaje (con su override de episodio vigente, si existe), cuando se genera la ficha técnica, entonces el resultado incluye un tipo de plano, un tipo de cámara y un tipo de iluminación, cada uno tomado del vocabulario técnico predefinido (RNF-04), sin valores fuera de esa lista.
- AC-07 (RF-07): Dado un plano generado por la IA (ej: "plano medio"), cuando el/la productor/a lo edita manualmente a otro valor de la lista (ej: "primer plano") y genera el prompt final, entonces el prompt resultante contiene "primer plano" y no el valor original generado por la IA.
- AC-08 (RF-08): Dado una ficha técnica ya generada o editada, cuando se arma el prompt final, entonces el prompt incluye plano + cámara + iluminación + descripción de personaje (con override de episodio vigente, si existe), sin ningún campo vacío.
- **AC-09 — Consistencia entre escenas (mide el objetivo del producto):** Dadas dos escenas distintas del mismo personaje dentro del mismo tramo de vigencia de override (o ambas sobre la hoja base, si no hay override), cuando se generan los prompts finales de ambas escenas, entonces los atributos de personaje (vestuario, edad, rasgos físicos) aparecen de forma idéntica, palabra por palabra, en los dos prompts.
- AC-10 (RNF-03): Dado que la llamada al modelo para generar una ficha técnica falla, cuando se agota el reintento automático, entonces la escena queda marcada como "pendiente" con aviso visible, y el resto de las escenas del episodio se procesan con normalidad.

## Fuera de Alcance

- Integración directa con herramienta de generación (el prompt se copia y pega manualmente).
- Generación o edición de imagen/video dentro de la app.
- Multi-usuario con roles/permisos, login complejo.
- Analítica de performance/monetización de episodios publicados.
- Vista tipo storyboard visual (solo texto en v1).
- Corrección o normalización automática de guiones mal formateados: en v1, un guion inválido se rechaza y se devuelve al/a la guionista para su corrección manual.
- Overrides de personaje a nivel escena (cambios temporales dentro de un mismo episodio, ej. una herida puntual): en v1 los overrides son solo a nivel episodio (RF-01b).
- Definición del contenido final del vocabulario técnico (los términos concretos de plano/cámara/iluminación): se define como entregable aparte, previo a la construcción de pantallas, no como parte de este documento.

## Riesgos y Dependencias

- Riesgo: la IA "invente" rasgos del personaje que contradigan la hoja (alucinación) → mitigación: siempre incluir la hoja de personaje completa (base + override vigente) como contexto en el prompt, y verificar la consistencia con AC-09.
- Riesgo: la terminología de cámara/iluminación generada no sea técnicamente válida o sea genérica → mitigación: usar salida estructurada del modelo con enums restringidos al vocabulario cerrado (RF-06, RNF-04), no texto libre validado después.
- Riesgo: un guion rechazado por formato inválido (RF-03) frena la producción hasta que el/la guionista lo corrija → aceptado como comportamiento de v1; queda como mejora futura ofrecer una normalización asistida.
- Riesgo: la falta de overrides a nivel escena deja sin resolver cambios puntuales dentro de un episodio (ej. personaje herido en una sola escena) → aceptado como limitación conocida de v1 (ver Fuera de Alcance).
- Dependencia: elección de proveedor de LLM (Claude, Gemini u otro) — decisión de implementación a formalizar, no atada al producto en sí.
- Dependencia: que el/la guionista entregue el guion siguiendo la convención de formato acordada (RF-03) — sin esto, el preprocesamiento determinístico no funciona.
- Dependencia: definición y acuerdo del contenido del vocabulario cerrado (RNF-04) antes de implementar RF-06 — es un entregable previo a la construcción de pantallas, no parte de este PRD.
